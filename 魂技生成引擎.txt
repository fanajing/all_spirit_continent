# 一、设计背景与问题分析

## 1.1 核心问题

AI 生成技能存在严重的**同质化**：

- 攻击武魂的所有魂技都是"伤害 + 眩晕"
- 多个魂环效果一样，没有差异化
- 魂兽特征只是表面关联，不能体现标志性机制
- 联动路径单一，只有"控制→伤害"和"削弱→伤害"两条

## 1.2 根因分析

| 原因 | 表现 |
|---|---|
| 安全优先 | AI 倾向选最不容易出错的原语组合 |
| 范例锚定 | 范例里的组合被反复模仿 |
| 温度过低 | 输出过于确定，缺乏变化 |
| 缺少反思 | AI 一次成型，不自我批判 |
| 约束太宽 | "自由发挥"等于"选最保守的" |
| 武魂主导 | 武魂特征压过魂兽特征 |

## 1.3 破解思路

```text
不是降低约束，而是：
  1. 先发散（生成多个候选方向）
  2. 再收束（按约束筛选）
  3. 后反思（自检是否同质化）
  4. 终优化（在保留随机性前提下修正）

同时：
  - 魂兽是技能的灵魂，武魂只是技能的载体
  - 用签名机制强制差异化
  - 用魂环定位区分不同环位
  - 用众包画像补全魂兽特征
```

## 1.4 关键设计决策

### 决策 1：不预置魂兽词条

不为每个 mod 生物手动写机制词条，而是让 AI 从魂兽描述中自行提取机制 + 众包观察补全。

### 决策 2：画像来自众包

玩家击杀魂兽时观察其行为，上传到云端聚合，形成"魂兽画像"。

### 决策 3：AI 从画像技能池组合

AI 不再凭空创造，而是从画像技能池中选择原语，按魂环定位组合。

### 决策 4：魂环定位是硬约束

不同环位有不同的原语数量、禁止原语、必须类别、伤害区间。

### 决策 5：签名机制强制差异化

每个技能必须选择一个签名机制，同一武魂不同魂环不得重复。

### 决策 6：原语与表现资源解耦

原语不直接绑定方块/粒子，而是调用注册表，支持 mod 覆盖和降级。

# 二、系统总览

## 2.1 目标

构建一套**基于众包画像与约束满足的魂技生成系统**：

- 玩家击杀魂兽 → 观察行为 → 生成魂技
- 多玩家观察数据众包聚合 → 魂兽画像持续完善
- AI 在画像与原语约束内组合魂技 → 保证合法性 + 差异化
- 表现资源解耦 → 兼容任意 mod

## 2.2 架构分层

```text
┌─────────────────────────────────────────────┐
│  表现层：魂技释放、粒子、音效、方块交互       │
├─────────────────────────────────────────────┤
│  生成层：AI 五阶段 + 数值反推 + JSON 校验      │
├─────────────────────────────────────────────┤
│  约束层：原语白名单 + 参数校验 + 魂环定位     │
├─────────────────────────────────────────────┤
│  画像层：行为观察 + 特征签名 + 本地缓存       │
├─────────────────────────────────────────────┤
│  云端层：上传去重 + 聚合 + 版本管理 + 拉取    │
├─────────────────────────────────────────────┤
│  数据层：实体属性 + 音效 + 粒子 + 掉落物      │
└─────────────────────────────────────────────┘
```

## 2.3 核心数据流

```text
玩家击杀魂兽
  → 事件监听记录行为
  → 生成 AbilitySignature
  → 本地画像缓存比对
  → 差异上传云端
  → 云端聚合更新画像
  → 本地拉取最新画像
  → AI 五阶段生成魂技
  → 约束校验
  → 数值反推
  → 写入魂环
```

## 2.4 模块划分

| 模块 | 职责 | 优先级 |
|---|---|---|
| `PrimitiveRegistry` | 原语注册、参数白名单、目标规则 | P0 |
| `SkillData` | 魂技数据结构、JSON 序列化 | P0 |
| `SkillValidator` | 校验原语/参数/target/定位 | P0 |
| `MobObserver` | 运行时监听魂兽行为 | P0 |
| `AbilitySignature` | 行为→签名映射 | P0 |
| `MobProfile` | 魂兽画像数据结构 | P0 |
| `ProfileCache` | 本地画像缓存 + 去重 | P0 |
| `CloudSync` | 上传/拉取/版本管理 | P1 |
| `ProfileAggregator` | 云端聚合逻辑（服务端） | P1 |
| `SkillGenerator` | AI 调用 + Prompt 组装 | P0 |
| `ValueCalculator` | 数值反推 | P0 |
| `ResourceResolver` | 表现资源解析 + 降级 | P1 |
| `RingPositionRules` | 魂环定位约束表 | P0 |
| `SignaturePool` | 签名机制池 + 随机抽取 | P0 |

# 三、原语系统

## 3.1 参数全集（19 个）

```text
value / radius / duration / target / damage_type / crit_chance /
attribute / percent / distance / direction / entity_id / count /
projectile_type / speed / effect / amplifier / growth_stage / sound / particle
```

| 参数 | 含义 | 类型 |
|---|---|---|
| value | 伤害量/治疗量/击退力度 | double |
| radius | 半径（格） | double |
| duration | 时长（tick，1秒=20tick） | int |
| target | SELF / TARGET | String |
| damage_type | MELEE/MAGIC/FIRE/EXPLOSION | String |
| crit_chance | 暴击率 0.0~1.0 | double |
| attribute | ATTACK_DAMAGE/MOVEMENT_SPEED/MAX_HEALTH | String |
| percent | 百分比 0.0~1.0 | double |
| distance | 距离（格） | double |
| direction | FORWARD/BACKWARD/TOWARD_TARGET/AWAY_FROM_TARGET/UP | String |
| entity_id | 实体注册名 | String |
| count | 数量 | int |
| projectile_type | 投射物注册名 | String |
| speed | 速度倍率 | double |
| effect | MobEffect 注册名 | String |
| amplifier | 效果等级（0 起） | int |
| growth_stage | 生长阶段增量 | int |
| sound | 音效注册名 | String |
| particle | 粒子类型注册名 | String |

## 3.2 原语全集（47 + 新增）

### 一、控制系（CONTROL）

| 原语 | 功能 | 允许参数 |
|---|---|---|
| BIND | 束缚（减速+移动锁定标记） | target, duration, radius |
| SILENCE | 沉默（禁止目标释放魂技） | target, duration |
| BLIND | 致盲 | target, duration, amplifier |
| ROOT | 定身（移动完全锁定） | target, duration |
| SLOW | 减速 | target, duration, amplifier |
| WEAKEN | 虚弱 | target, duration, amplifier |
| CONFUSE | 混乱（反胃效果） | target, duration |
| DISARM | 缴械（主手掉落并清空） | target, radius |
| **WEB** | **发射蛛网投射物，命中生成蛛网区域** | **target, distance, duration, radius, speed** |

**WEB 行为逻辑：**

```text
1. 从玩家位置朝鼠标方向发射蛛网投射物
2. 投射物命中实体或地面时，在命中点半径 radius 内生成蛛网方块
3. 蛛网持续 duration tick 后自动消失
4. 若命中实体，则该实体立即被蛛网困住
5. 若 radius > 0，则生成多个蛛网方块，形成一片网区
```

**WEB 与 BIND 的区别：**

| 维度 | BIND | WEB |
|---|---|---|
| 本质 | 状态效果 | 真实方块实体 |
| 视觉 | 粒子/无 | 原版蛛网方块 |
| 可互动 | 不能被打断 | 可被火烧、可被破坏 |
| 范围 | 立即生效 | 投射物命中后生成 |
| 手感 | 抽象控制 | 物理控场 |
| 适用场景 | 快速控制 | 阵地控制、封路、陷阱 |

## 3.3 被动白名单（passive 专用）

```text
ACCELERATE / BUFF_STATS / BUFF_ALL / HOT / SHIELD_TRANSFER /
CLEANSE / REFLECT / BARRIER / PHANTOM / PARTICLE
```

**规则：**

- target 必须为 SELF
- 禁止伤害/控制/召唤混入
- 这些原语同样可用于主动 execution

## 3.4 目标规则

### 伤害/减益/控制类（target 必须为 TARGET）

```text
BURST / AOE_DAMAGE / AOE_BURST / ARMOR_BREAK / EXECUTE / COMBO /
BACKSTAB / CHARGE / FIRE / PROJECTILE / KNOCKBACK / POTION /
SLOW / BLIND / ROOT / WEAKEN / CONFUSE / STUN / BIND / SILENCE /
DISARM / WEB
```

### 增益/治疗/防御/位移类（target 为 SELF）

```text
ACCELERATE / BUFF_STATS / BUFF_ALL / HOT / REVIVE / REFLECT /
BARRIER / IRON_BODY / HARDEN / PHANTOM / EVADE / CLEANSE /
SHIELD_TRANSFER / DASH / TAUNT
```

**例外：** HOT / REVIVE / CLEANSE / SHIELD_TRANSFER 想治疗队友时可用 TARGET。

### AOE 特殊规则

```text
AOE_DAMAGE / AOE_BURST 以 target 为圆心，target 必须为 TARGET；
省略 target 时默认以自身为圆心且不会伤害自己。
```

### 表现类（无 target 规则）

```text
SOUND / PARTICLE
```

## 3.6 原语扩展指南

### 新增原语必须满足

1. **原子性**：不可再分，不是复合效果
2. **参数统一**：复用现有 19 个参数
3. **目标明确**：归属三类之一
4. **数量控制**：总量不超过 70~80 个
5. **同步更新**：System Prompt + 范例 + 目标规则

| P0 | MARK | 叠加印记 | target, count, duration | 印记流 |
| P0 | DETONATE | 引爆印记 | target, value, radius | 印记终结 |
| P0 | DOMAIN | 生成持续领域 | radius, duration, effect | 领域控场 |
| P1 | CHAIN | 伤害弹射 | target, value, count, radius | 群体连锁 |
| P1 | FEAR | 恐惧 | target, duration, radius | 控制新维度 |
| P1 | SOUL_LINK | 灵魂链接 | target, duration, percent | 巫妖王灵魂操控 |
| P2 | TERRAIN | 改变地形 | radius, duration | 地形战术 |
| P2 | VORTEX | 吸引漩涡 | radius, duration, value | 聚怪神技 |
| P2 | LIGHTNING | 召唤闪电 | target, radius, value | 雷系武魂 |
| P3 | DELAY | 延迟引爆 | target, duration, value | 陷阱流 |
| P3 | REWIND | 时光倒流 | duration | 高阶玩法 |

### 原语总数警告

```text
47 个原语已接近 AI 能稳定处理的临界点。
超过 70~80 个后：
  - AI 会混淆原语
  - 参数容易写错
  - 生成质量下降
  - Prompt 超长，成本上升

解决方案：按武魂系别动态裁剪原语列表。
```

# 四、魂环定位规则

## 4.1 定位表

| 环 | 名称 | 原语数 | 禁止 | 必须包含 | 伤害占比 |
|---|---|---|---|---|---|
| 1 | 基础启动技 | 1~2 | 范围伤害 | - | 3%~5% |
| 2 | 辅助输出/续航 | 1~2 | 斩杀 | 1个非伤害原语 | 4%~6% |
| 3 | 真正战斗技 | 2~3 | 纯数值堆叠 | 1个核心机制 | 6%~10% |
| 4 | 强力大招 | 2~3 | 无控制纯伤害 | - | 12%~18% |
| 5 | 强化自身 | 1~2 | 对敌伤害 | 全部SELF | 0 |
| 6 | 大范围必杀 | 2~3 | 单体为主 | AOE radius≥5 | 5%~8% |
| 7 | 武魂真身 | 3~4 | SUMMON_ENTITY | 2种类别 | 15%~20% |
| 8 | 双大招 | 4 | 4个全伤害 | 2种伤害机制 | 20%~25% |
| 9 | 终极必杀 | 4 | - | 终结机制 | 25%~30% |

## 4.2 每个环位的详细约束

### 第 1 环：基础启动技

```text
应该做：单体伤害 / 小增益
禁止做：范围伤害、超过 2 个原语
签名机制池：A / B / E
```

### 第 2 环：辅助输出/续航

```text
应该做：小控制 / 续航 / 位移
禁止做：斩杀、AOE_BURST
必须包含：至少 1 个非伤害原语（控制/治疗/位移/增益）
签名机制池：A / B / E
```

### 第 3 环：真正战斗技

```text
应该做：核心机制（召唤/领域/印记等）
禁止做：纯数值堆叠
必须包含：1 个核心机制
签名机制池：A / D / F / G
```

### 第 4 环：强力大招

```text
应该做：高伤+控制联动
禁止做：无控制/无破甲的纯伤害
签名机制池：A / D / F / G
```

### 第 5 环：强化自身

```text
应该做：全属性大幅提升
禁止做：对敌伤害原语
必须：全部作用于 SELF
签名机制池：B / C / L
```

### 第 6 环：大范围必杀

```text
应该做：AOE_DAMAGE 或 AOE_BURST 为核心
禁止做：单体为主
必须：radius ≥ 5
签名机制池：G / H / K
```

### 第 7 环：武魂真身

```text
应该做：玩家自身进入爆发状态，武魂虚影具象化
禁止做：
  - 禁止 SUMMON_ENTITY
  - 禁止出现"召唤巨大XX"或"变成XX"的描述
  - 禁止召唤真身实体
必须：核心是自身强化 + 至少 2 种类别
允许：搭配 1~2 个对敌原语
视觉表现：只可用 PARTICLE / SOUND
签名机制池：D / L / M
```

### 第 8 环：双大招

```text
应该做：两种不同的伤害机制
禁止做：4 个原语全是对敌伤害
签名机制池：F / I / J / N
```

### 第 9 环：终极必杀

```text
应该做：终结机制 + 视觉表现
必须：终结机制（斩杀/领域/大型召唤）
允许：超越常规的数值
签名机制池：F / I / J / N
```

## 4.4 数值规则

### 公式

```text
系统最终伤害 = value × 原语系数 × 年限倍率
```

### 年限倍率

| 年限 | 倍率 |
|---|---|
| 十年 | ×1 |
| 百年 | ×2 |
| 千年 | ×4 |
| 万年 | ×8 |
| 十万年 | ×16 |
| 百万年 | ×32 |

### 原语系数

| 原语 | 系数 |
|---|---|
| BURST | ×2 |
| AOE_BURST | ×1.5 |
| AOE_DAMAGE | ×1 |
| COMBO | ×1（每段） |
| BACKSTAB | ×2.5 |
| ARMOR_BREAK | ×1.2 |
| EXECUTE | ×4（斩杀）/ ×1（普通） |
| CHARGE | ×1（贯穿） |

### 设计目标

```text
单体技能单发：约魂兽最大生命的 8%~15%
范围技能单发：约 3%~6%
斩首/终结技：20% 以上
```

### value 反推

```text
value = 目标单发伤害 ÷ 原语系数 ÷ 年限倍率
```

### EXECUTE 特别说明（重要修正）

**当前设计中 EXECUTE 的数值模型存在矛盾，必须修正：**

```text
原设计问题：
- 范例中 value=100，斩杀线=200 血，斩杀伤害=12800（倍率32）
- 但目标满血 600000，斩杀线仅占 0.033%，几乎无意义
- 规则说"斩杀线为 2%~4% 满血"，差 60~120 倍

修正建议：
- value 直接表示斩杀线血量，不再通过 value×2 间接推导
- 斩杀伤害 = value × 斩杀系数（单独定义，如 0.1~0.2）× 年限倍率
- 或者干脆从"按满血百分比反推"中移除 EXECUTE
```

### 治疗/护盾

```text
value 约为玩家生命值(20点)的 30%~60% ÷ 年限倍率
SHIELD_TRANSFER 用 amplifier 表示护盾强度(1~4)，duration 表示持续(秒×20)
```

### 被动

```text
duration 统一给 200（10秒，系统每 2 秒自动续杯）
amplifier 1~3
BUFF_STATS 的 percent 给 0.1~0.5
```

### 其他参考

```text
radius 2~8
duration 40~200
cooldown 10~80
减益/增益效果等级不超过 2
```

```java
        AbilitySignature cached = localProfile.findSimilar(sig);
```

```java
MobProfile aggregate(String entityId, String modVersion, List<Upload> uploads) {
    MobProfile merged = store.get(entityId, modVersion);
    
    for (Upload u : uploads) {
        for (AbilitySignature sig : u.abilities) {
            AbilitySignature existing = merged.find(sig);
            if (existing == null) {
                merged.add(sig.copyWithConfidence(0.3f));
            } else {
                existing.confidence = Math.min(1.0f, existing.confidence + 0.1f);
                existing.params = averageParams(existing.params, sig.params);
                existing.observedCount += sig.observedCount;
            }
        }
        merged.contributorCount++;
    }
    
    merged.abilities.removeIf(a -> a.confidence < 0.3f);
    merged.abilities.sort(byConfidenceDesc);
    return merged;
}
```

## 6.4 批量上传

```java
class UploadQueue {
    ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
    
    void start() {
        scheduler.scheduleAtFixedRate(this::flush, 5, 5, TimeUnit.MINUTES);
    }
    
    void flush() {
        if (queue.isEmpty()) return;
        List<Upload> batch = new ArrayList<>(queue);
        queue.clear();
        try {
            httpClient.post("/api/v1/profile/batch-upload", batch);
        } catch (Exception e) {
            queue.addAll(batch);
        }
    }
}
```

# 七、AI 生成模块

## 7.1 设计哲学

```text
不是降低约束，而是：
  1. 先发散（生成多个候选方向）
  2. 再收束（按约束筛选）
  3. 后反思（自检是否同质化）
  4. 终优化（在保留随机性前提下修正）
```

## 7.2 五阶段流程

```text
阶段1：魂兽机制分析（发散，温度 0.7）
  ↓
阶段2：签名机制选择（随机 + 去重，温度 1.0）
  ↓
阶段3：原语组合草案（多候选，温度 1.0）
  ↓
阶段4：自检反问（批判，温度 0.3）
  ↓
阶段5：JSON 输出（收束，温度 0.2）
```

## 7.3 阶段1：魂兽机制分析

### Prompt 片段

```text
【第一步：魂兽机制分析】
在生成技能前，请先完成以下分析（仅在思考中执行）：

1. 这只魂兽最标志性的 3 个行为是什么？
   例如：巫妖王 = 六面护盾、召唤仆从、瞬移
   例如：蜘蛛 = 织网、毒液、伏击
   例如：苦力怕 = 蓄力、自爆、范围爆炸

2. 它的战斗节奏是怎样的？
   例如：先远程消耗→再召唤→最后近战狂暴

3. 它的视觉/听觉特征是什么？
   例如：灵魂火粒子、亡灵音效、冰霜气息

4. 如果用一句话概括它的核心机制，是什么？
   例如：巫妖王 = 护盾不破则无敌，破盾后召唤亡灵大军

分析完成后，进入第二步。
```

### 自检

```text
自检1：如果把魂兽名字换成另一个生物，这个分析还成立吗？
  如果成立 → 分析太泛，重新分析

自检2：分析里是否至少有一个"非伤害"机制？
  如果没有 → 说明只关注了伤害，重新分析
```

## 7.4 阶段2：签名机制选择

### 签名机制池

```text
【可选签名机制】（每次随机抽取一个，同一武魂不同魂环不得重复）

A. 印记爆发：先叠加印记，后引爆造成额外伤害
B. 吸血续航：造成伤害转化为自身治疗
C. 护盾反击：先吸收伤害，后反弹
D. 召唤协同：召唤仆从，自身获得增益
E. 位移连段：突进→连击→撤离
F. 斩杀收割：削弱→处决→获取增益
G. 领域控场：范围限制 + 持续削弱
H. 连锁反应：伤害在多个目标间弹射
I. 蓄力爆发：延迟引爆，伤害随时间累积
J. 灵魂操控：与目标建立链接，共享伤害/状态
K. 地形改造：改变战场地形（冰面/岩浆/藤蔓）
L. 分身幻影：制造幻影，迷惑敌人
M. 生命献祭：消耗自身生命换取强力效果
N. 时间延迟：效果延迟生效，预判打击
O. 反向治疗：将敌人的治疗转化为伤害
```

### 随机抽取规则

```text
1. 从签名机制池中随机抽取 1 个
2. 排除当前武魂已使用的签名机制
3. 排除与魂环定位不匹配的签名机制
   - 1~2环：优先 A/B/E
   - 3~4环：优先 A/D/F/G
   - 5环：优先 B/C/L
   - 6环：优先 G/H/K
   - 7环：优先 D/L/M
   - 8~9环：优先 F/I/J/N
```

### Prompt 片段

```text
【第二步：签名机制】
本次抽取的签名机制是：{signatureMechanism}

请围绕这个签名机制设计技能，禁止偏离。
如果你的设计与签名机制无关，将被系统拒绝。
```

### 自检

```text
自检3：技能的核心玩法是否可以用一句话描述为"签名机制"？
  如果不能 → 重新设计

自检4：如果把签名机制换掉，技能是否仍然成立？
  如果仍然成立 → 说明签名机制没有真正融入，重新设计
```

## 7.5 阶段3：原语组合草案

### Prompt 片段

```text
【第三步：原语组合草案】
```

## 7.6 阶段4：自检反问

### 10 项自检清单

```text
【第四步：自检反问】
请对你选择的候选组合进行以下自检，并如实回答：

1. 同质化自检：
   这个技能和"伤害+控制"的万能模板有什么区别？
   如果答不上来 → 重新设计

2. 魂兽自检：
   如果把魂兽换成另一个生物，这个技能还成立吗？
   如果成立 → 魂兽特征不够强，重新设计

3. 签名自检：
   技能的核心玩法是否可以用签名机制一句话概括？
   如果不能 → 重新设计

4. 联动自检：
   多个原语之间是否形成了因果链？
   （例如：破甲→爆发更痛，减速→更容易命中）
   如果没有联动，只是数值堆叠 → 重新设计

5. 定位自检：
   技能是否符合第 {ringIndex} 环的定位？
   （例如：2环不该有斩杀，5环不该有对敌伤害）
   如果不符合 → 调整原语

6. 目标自检：
   伤害/控制原语的 target 是否都是 TARGET？
   增益/防御原语的 target 是否都是 SELF？
   如果有错误 → 修正

7. 参数自检：
   每个原语的参数是否都在白名单内？
   是否有必填参数遗漏？
   如果有错误 → 修正

8. 数值自检：
   value 是否按公式反推？
   是否在魂环定位的伤害区间内？
   如果超出 → 重新计算

9. 表现自检：
   是否有至少 1 个表现原语（PARTICLE/SOUND）？
   表现是否与魂兽主题契合？
   如果没有 → 补充

10. 独特性自检：
    这个技能和同一武魂其他魂环的技能是否明显不同？
    如果雷同 → 重新设计
```

### 反问式自检

```text
【反问式自检】
请用以下反问句挑战自己的设计：

Q1：如果玩家看到这个技能，会不会觉得"又是一个伤害+控制"？
   回答"会" → 重新设计

Q2：这个技能的签名机制，能否在技能名里体现出来？
   如果不能 → 说明签名机制不够核心

Q3：如果把这个技能给另一个魂兽，会不会更合适？
   如果会 → 说明魂兽特征不够强

Q4：这个技能是否有一个"让玩家记住"的瞬间？
   （例如：破盾的瞬间、斩杀线触发的瞬间、召唤物出现的瞬间）
   如果没有 → 补充一个机制亮点

Q5：如果只能保留一个原语，你会保留哪个？
   这个原语是否就是技能的核心？
   如果不是 → 重新调整原语顺序
```

```text
自检4失败 → 回到阶段2强化签名机制
自检5失败 → 回到阶段3重新生成候选
自检6失败 → 回到阶段3修正偏离的候选
自检7失败 → 回到阶段3替换万能组合
自检8失败 → 回到阶段3调整原语
自检9失败 → 回到阶段3补充表现
自检10失败 → 回到阶段3重新设计
```

## 7.7 阶段5：JSON 输出

### 输出前最终检查

```text
【第五步：输出 JSON】
```

# 八、校验、降级与数值反推

## 8.1 校验器

```java
class SkillValidator {
    ValidationResult validate(SkillData skill, RingPositionRule rule, 
                               List<AbilitySignature> pool) {
        List<String> errors = new ArrayList<>();
        
        // 1. 原语数量
        int n = skill.execution.size();
        if (n < rule.minPrimitives || n > rule.maxPrimitives) {
            errors.add("原语数量 " + n + " 超出 [" + rule.minPrimitives + "," + rule.maxPrimitives + "]");
        }
        
        // 2. 逐个校验原语
        for (PrimitiveStep step : skill.execution) {
            PrimitiveDef def = registry.get(step.primitive);
            if (def == null) {
                errors.add("未知原语: " + step.primitive);
                continue;
            }
            
            // 参数白名单
            for (String key : step.params.keySet()) {
                if (!def.allowedParams.contains(key)) {
                    errors.add(step.primitive + " 不允许参数 " + key);
                }
            }
            
            // 必填参数
            for (String req : def.requiredParams) {
                if (!step.params.containsKey(req)) {
                    errors.add(step.primitive + " 缺少必填参数 " + req);
                }
            }
            
            // target 规则
            String target = (String) step.params.get("target");
            if (def.targetRule == MUST_TARGET && !"TARGET".equals(target)) {
                errors.add(step.primitive + " target 必须为 TARGET");
            }
            if (def.targetRule == MUST_SELF && !"SELF".equals(target)) {
                errors.add(step.primitive + " target 必须为 SELF");
            }
        }
        
        // 3. 禁止原语
        for (PrimitiveStep step : skill.execution) {
            if (rule.forbiddenPrimitives.contains(step.primitive)) {
                errors.add(step.primitive + " 在 " + rule.name + " 被禁止");
            }
        }
        
        // 4. 必须类别
        Set<PrimitiveCategory> categories = skill.execution.stream()
            .map(s -> registry.get(s.primitive).category)
            .collect(toSet());
        for (String required : rule.requiredCategories) {
            if (!categories.contains(PrimitiveCategory.valueOf(required))) {
                errors.add("缺少必须类别: " + required);
            }
        }
        
        // 5. 被动校验
        if (skill.passive != null) {
            for (PrimitiveStep step : skill.passive) {
                if (!PASSIVE_WHITELIST.contains(step.primitive)) {
                    errors.add("passive 不允许 " + step.primitive);
                }
                String target = (String) step.params.get("target");
                if (!"SELF".equals(target)) {
                    errors.add("passive target 必须为 SELF");
                }
            }
        }
        
        return new ValidationResult(errors.isEmpty(), errors);
    }
}
```

```text
2. AI 输出非法 → 反馈错误，重试 1 次
```

## 8.3 数值反推

```java
class ValueCalculator {
    void calibrate(SkillData skill, MobProfile profile, int ringIndex) {
        double maxHealth = profile.attributes.maxHealth;
        double ratio = RingPositionRules.get(ringIndex).getDamageRatio();
        double targetDamage = maxHealth * ratio;
        
        for (PrimitiveStep step : skill.execution) {
            double coefficient = PRIMITIVE_COEFFICIENT.getOrDefault(step.primitive, 1.0);
            double yearMultiplier = YEAR_MULTIPLIER.get(ringIndex);
            
            if (step.params.containsKey("value")) {
                double value = targetDamage / coefficient / yearMultiplier;
                step.params.put("value", round(value, 2));
            }
        }
    }
    
    static Map<String, Double> PRIMITIVE_COEFFICIENT = Map.of(
        "BURST", 2.0,
        "AOE_BURST", 1.5,
        "AOE_DAMAGE", 1.0,
        "COMBO", 1.0,
        "BACKSTAB", 2.5,
        "ARMOR_BREAK", 1.2,
        "EXECUTE", 4.0,
        "CHARGE", 1.0
    );
    
    static Map<Integer, Double> YEAR_MULTIPLIER = Map.of(
        1, 1.0, 2, 2.0, 3, 4.0, 4, 8.0, 5, 16.0,
        6, 32.0, 7, 32.0, 8, 32.0, 9, 32.0
    );
}
```

**注意：EXECUTE 的 value 语义需单独定义，不要和普通伤害共用公式。**

## 9.1 核心思路

```text

问题：mod 怪物有原版没有的表现资源（如虚空方块、灵魂火焰）
```


## 9.3 降级链

```text

2. 关键词扫描 → 80% 还原
3. 原版回退 → 70% 还原
4. 状态效果降级 → 40% 还原
```

## 9.4 自动扫描

```text
启动时扫描所有已注册的方块/实体/粒子
按关键词分类：
  - 含 "web" / "silk" / "net" / "trap" → 网类
  - 含 "fire" / "flame" → 火类
  - 含 "ice" / "frost" / "freeze" → 冰类
  - 含 "poison" / "toxic" → 毒类
  - 含 "soul" / "spirit" → 灵魂类
  - 含 "void" → 虚空类
  - 含 "lightning" / "thunder" → 雷类
```

## 9.5 AI 语义分类

```text
当关键词匹配失败时，让 AI 帮忙处理命名不规范的情况：

把无法识别的资源名发给 AI：
  "以下方块名是某个 mod 的方块，请判断它最接近以下哪一类：
   网类 / 火类 / 冰类 / 毒类 / 灵魂类 / 虚空类 / 雷类 / 其他"

AI 返回分类结果 → 缓存 → 下次直接用
```

# 十三、注意事项

## 13.1 性能

```text
1. 事件监听要轻量，只在事件触发时记录
2. 画像缓存要持久化（NBT 或 JSON）
3. AI 调用要超时（10 秒），失败走本地降级
4. Prompt 长度要控制，技能池只传置信度 ≥ 0.5 的，最多 20 条
```

## 13.2 兼容

```text
1. 原语与表现资源解耦，支持 mod 覆盖和自动扫描
2. 实体 ID 用完整 modid:entity_id，避免冲突
3. 版本指纹精确匹配，mod 更新后旧画像不用于新版本
4. 环境隔离：基础画像 + 环境增强画像分开存储
```

## 13.3 隐私

```text
1. 只上传匿名化行为特征
2. 不做玩家 ID 绑定
3. 明确告知数据用途
4. 提供"关闭上传"选项
```

## 13.4 安全

```text
1. 数据污染 → 置信度机制 + 多玩家交叉验证
2. 恶意伪造 → 异常检测 + 黑名单
3. 上传频率限制 → 批量 + 延迟上传
```

## 13.5 扩展

```text
1. 原语总数控制在 70~80 个以内
2. 超过后按武魂系别动态裁剪
3. 新原语必须原子性、参数统一、目标明确
4. 每新增原语，同步更新 System Prompt + 范例
```

## 13.6 平衡

```text
1. EXECUTE 的 value 语义单独定义
2. 数值反推以魂兽最大生命为基准
3. 魂环定位的伤害区间是硬约束
4. 被动 duration 统一 200，amplifier 1~3
```

## 13.7 关键警告

```text
1. temperature 0.9 太高，必须分阶段控制温度
2. EXECUTE 数值模型自相矛盾，必须先修正
3. 生活系原语（CROP_GROW 等）不应在战斗技能中出现
4. 参数必填/可选未明确，会导致步骤被丢弃
5. 范例必须全部正确，否则会毒化 AI
6. 武魂真身禁止召唤实体，必须是自身爆发
```

## 文档总结

**核心原则：**

1. **约束内随机**：随机性只作用于"选哪个合法解"，不作用于"是否合法"
2. **画像驱动生成**：AI 从画像技能池组合，不再凭空创造
3. **五阶段自检**：分析 → 签名 → 草案 → 自检 → 输出
4. **魂兽主导**：魂兽是灵魂，武魂是载体
5. **表现资源解耦**：原语调用注册表，支持 mod 覆盖和降级
6. **众包画像**：多玩家观察聚合，置信度机制防污染
7. **魂环定位差异化**：9 个环位各有定位和约束
8. **签名机制不重复**：同一武魂不同魂环签名不得重复

**关键风险：**

1. EXECUTE 数值模型矛盾，必须修正
2. temperature 0.9 太高，必须分阶段控制
3. 生活系原语不应在战斗技能中出现
4. 武魂真身禁止召唤实体
5. 范例必须正确，否则毒化 AI

**文档版本：** v2.0 完整版

**目标用户：** 实现该系统的代码 AI
